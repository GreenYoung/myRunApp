# 高德地图道路级显示与轨迹纠偏分阶段提示词

请基于当前 Android 项目，分阶段优化高德地图轨迹展示精度。

本提示词包含三个阶段：

```text
1. 提高地图 zoom 到道路级
2. 做 WGS84 -> GCJ-02 坐标转换
3. 评估猎鹰轨迹纠偏
```

请严格按阶段执行，不要一次性把三步全部混在一起实现。每个阶段完成后都需要单独编译和真机验证。

## 0. 当前背景

项目当前已经实现：

- 高德轻量地图合包 AAR 已接入。
- `RunTrackingScreen` 使用高德地图全屏展示实时跑步轨迹。
- `RunTrackDetailScreen` 使用高德地图展示历史轨迹预览。
- 实时轨迹点来自 `RunTrackingUiState.trackPoints`。
- 历史轨迹点来自 `RunTrackPointEntity`。
- 地图绘制当前直接使用：

```kotlin
LatLng(latitude, longitude)
```

当前可能存在的问题：

- 地图缩放不够接近道路级。
- GPS 原始坐标可能是 WGS84，而高德底图使用 GCJ-02，轨迹可能整体偏移。
- 即使坐标系正确，GPS 点仍可能因为漂移、不走路网而看起来没有贴合道路。

## 阶段一：提高地图 zoom 到道路级

### 1.1 目标

让实时跑步地图和轨迹详情地图默认展示得更接近道路级。

本阶段只调整地图镜头策略，不修改轨迹点坐标、不修改 GPS 采集、不修改距离计算。

### 1.2 修改范围

优先检查并修改：

```text
AMapRunTrackingMap.kt
AMapTrackPreview.kt
```

可能涉及的方法：

```kotlin
followLiveTrack(...)
moveToTrack(...)
```

### 1.3 实时跑步地图 zoom

当前实时地图跟随最新点时可能使用：

```kotlin
CameraUpdateFactory.newLatLngZoom(latestPoint, 17f)
```

建议改为：

```kotlin
CameraUpdateFactory.newLatLngZoom(latestPoint, 18f)
```

如果真机效果仍不够细，可以评估：

```text
18.5f
19f
```

但第一版建议先使用：

```text
18f
```

避免地图过度放大导致轨迹抖动更明显。

### 1.4 历史轨迹详情地图 zoom

历史轨迹详情目前会根据完整轨迹范围自动缩放。

建议：

- 有 1 个有效点时，使用：

```kotlin
newLatLngZoom(point, 18f)
```

- 有多个点时，继续使用 `LatLngBounds` 自动缩放。
- 适当减小 bounds padding，例如从 `80px` 调整为：

```text
48px ~ 64px
```

让地图看起来更接近道路。

不要为了道路级强行对很长轨迹使用固定 `18f`，否则长距离轨迹会看不完整。

### 1.5 验收标准

- 跑步中地图能看清附近道路。
- 轨迹详情页单点或短轨迹更接近道路级。
- 长距离历史轨迹仍能完整显示。
- 不影响轨迹保存和距离计算。

### 1.6 测试

执行：

```text
testDebugUnitTest
assembleRelease
```

真机测试：

1. 安装 release APK。
2. 进入户外跑步页。
3. 开始跑步。
4. 观察地图是否更接近道路级。
5. 结束保存。
6. 查看轨迹详情页是否仍能完整展示轨迹。

## 阶段二：WGS84 -> GCJ-02 坐标转换

### 2.1 目标

解决 Android 原生 GPS 坐标直接绘制到高德地图后，可能相对道路和底图整体偏移的问题。

高德底图使用 GCJ-02 坐标系，而 Android 原生 GPS 通常返回 WGS84。用于地图展示时，应将 WGS84 转换为 GCJ-02。

### 2.2 重要原则

本阶段只转换“地图展示坐标”。

不要修改：

- 数据库中保存的原始轨迹点。
- `RunTrackPointEntity.latitude / longitude`。
- 距离计算逻辑。
- GPS 过滤逻辑。
- 已保存历史数据。

也就是说：

```text
存储和距离统计：继续使用原始 GPS 坐标
地图展示：使用转换后的 GCJ-02 坐标
```

### 2.3 修改范围

优先改动：

```text
AMapRunTrackingMap.kt
AMapTrackPreview.kt
```

建议新增统一坐标转换工具：

```text
app/src/main/java/com/example/myrunapp/feature/run/CoordinateTransform.kt
```

或者：

```text
app/src/main/java/com/example/myrunapp/core/location/CoordinateTransform.kt
```

如果当前项目没有 core location 包，优先放在：

```text
feature/run
```

### 2.4 API 设计建议

新增：

```kotlin
data class MapCoordinate(
    val latitude: Double,
    val longitude: Double
)
```

或直接返回高德：

```kotlin
fun wgs84ToGcj02(latitude: Double, longitude: Double): Pair<Double, Double>
```

建议封装：

```kotlin
fun RunTrackPointUiModel.toMapLatLng(): LatLng {
    val converted = CoordinateTransform.wgs84ToGcj02(latitude, longitude)
    return LatLng(converted.latitude, converted.longitude)
}
```

### 2.5 中国境外判断

GCJ-02 转换只适用于中国大陆范围。

需要加入判断：

```kotlin
fun isOutsideChina(latitude: Double, longitude: Double): Boolean
```

如果坐标在中国境外：

```text
直接返回原始 WGS84
```

避免海外坐标被错误偏移。

### 2.6 转换算法

可以使用常见 WGS84 -> GCJ-02 算法，包含：

```text
transformLat
transformLng
earth radius
eccentricity
```

要求：

- 使用 `Double`。
- 不引入大型第三方库。
- 不联网。
- 不修改原始数据。
- 添加单元测试。

### 2.7 单元测试建议

新增测试文件：

```text
app/src/test/java/com/example/myrunapp/feature/run/CoordinateTransformTest.kt
```

测试内容：

- 中国大陆坐标转换后不等于原坐标。
- 境外坐标转换后等于原坐标。
- 非法边界坐标不崩溃。
- 转换结果在合理范围内。

示例：

```text
深圳 / 杭州 / 北京坐标：转换后有轻微偏移
纽约 / 东京坐标：保持不变
```

### 2.8 验收标准

- 地图上的实时轨迹更贴近高德底图道路。
- 历史轨迹详情页同样使用转换后的展示坐标。
- 数据库保存的原始经纬度不变。
- 距离、配速、卡路里结果不变。
- 单元测试通过。

### 2.9 测试

执行：

```text
testDebugUnitTest
assembleRelease
```

真机测试：

1. 记录一段道路边跑步或步行轨迹。
2. 观察实时地图轨迹是否整体偏移减少。
3. 结束后查看详情页轨迹是否同样贴近底图。
4. 对比距离是否没有异常变化。

## 阶段三：评估猎鹰轨迹纠偏

### 3.1 目标

评估是否需要接入高德猎鹰轨迹服务，实现更进一步的道路吸附、轨迹纠偏、轨迹回放或云端轨迹管理。

本阶段先做技术评估，不直接接入生产功能，除非用户明确确认。

### 3.2 适用场景

猎鹰轨迹纠偏适合：

- GPS 点已经转换到高德坐标系，但轨迹仍然不贴路。
- 城市道路、高架、建筑密集区漂移明显。
- 希望轨迹自动贴合道路。
- 希望做云端轨迹回放。
- 希望做轨迹点上云管理。

不适合第一版直接接入的原因：

- 需要服务端或云服务配置。
- 可能需要创建 Terminal / Track。
- 需要上传轨迹点。
- 涉及网络失败处理。
- 涉及用户隐私说明。
- 可能影响实时性和成本。

### 3.3 评估内容

需要调研并输出一份评估文档：

```text
docs/高德猎鹰轨迹纠偏评估.md
```

文档至少包含：

- 猎鹰 SDK / Web API 需要哪些能力。
- 是否需要额外高德服务 Key。
- 是否需要服务端参与。
- 是否支持 Android 端直接调用。
- 轨迹纠偏输入字段：
  - 经度
  - 纬度
  - 时间戳
  - 速度
  - 方向
  - 精度
- 输出字段：
  - 纠偏后坐标
  - 距离
  - 道路匹配信息
- 是否能离线使用。
- 网络失败如何降级。
- 是否保存原始轨迹和纠偏轨迹两份数据。
- 对现有数据库 Schema 的影响。
- 对隐私合规的影响。

### 3.4 推荐数据设计

如果后续接入猎鹰，不要覆盖原始轨迹。

建议数据分层：

```text
RawTrackPoint：原始 GPS 点
DisplayTrackPoint：地图展示坐标，WGS84 -> GCJ-02
CorrectedTrackPoint：猎鹰纠偏后的轨迹点
```

数据库可以后续新增：

```text
run_corrected_track_points
```

或者在现有点表中新增字段，但这需要单独迁移评审。

第一版评估阶段不要修改数据库。

### 3.5 降级策略

如果猎鹰纠偏失败：

```text
优先显示 GCJ-02 转换后的轨迹
```

不要让地图无轨迹。

如果网络不可用：

```text
保存原始轨迹
稍后再纠偏
```

但“稍后纠偏”属于后续功能，本阶段只评估。

### 3.6 验收标准

阶段三只要求产出评估文档，不要求接入代码。

评估文档必须回答：

- 是否建议接入猎鹰。
- 建议接入时机。
- 需要新增哪些模块。
- 是否需要后端。
- 是否要新增数据库表。
- 对现有功能的影响。
- 预估开发量。

## 总体执行顺序

严格按以下顺序：

```text
阶段一：提高 zoom
↓
编译 + 真机验证
↓
阶段二：坐标转换
↓
单元测试 + 编译 + 真机验证
↓
阶段三：猎鹰评估文档
```

不要跳过阶段一直接做猎鹰。

不要在阶段二修改数据库。

不要在阶段三未经确认直接接入猎鹰 SDK 或 API。

## 总体验收标准

最终应满足：

- 地图展示更接近道路级。
- 实时跑步页和轨迹详情页表现一致。
- 坐标转换只影响地图展示，不影响原始数据和距离统计。
- 历史轨迹仍能正常显示。
- 构建通过。
- 每个阶段的改动范围清晰可回退。
