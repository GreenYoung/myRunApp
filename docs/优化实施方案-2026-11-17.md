## 1. P0 体验硬伤

### 1.1 暂停时停止定位

**目标**：暂停期间不再有 GPS 回调与耗电；恢复后轨迹连续、不把暂停期间的位置算进距离。

**现状**：`RunTrackingService.pauseTracking()`（`:258-278`）只置 `isPaused` + 释放 wakelock，AMap 客户端仍在 1s 回调，`handleLocation()` 里丢弃（`:640`）。

**方案**：复用已有的 start/stop 能力，不改过滤逻辑。

```kotlin
private fun pauseTracking() {
    if (!current.isTracking || current.isPaused || isSaving) return
    pausedAtMs = System.currentTimeMillis()
    stopLocationUpdates()                    // ← 新增：暂停即停定位
    RunTrackingStateStore.update {
        it.copy(isPaused = true, gpsStatusText = "已暂停（定位已关闭）", errorMessage = null)
    }
    releaseWakeLock()
    persistDraftSnapshot(force = true)
    updateNotification()
}

private fun resumeTracking() {
    ...
    skipNextAcceptedPoint = true             // 已有：恢复后首个点只做基线
    gpsTrackFilter.reset()                   // 已有
    startAmapLocationUpdates()               // ← 新增：内部会先 stop 再 start，幂等
    resetLocationHealthWatch()
}
```

**注意**：

- `startAmapLocationUpdates()`（`:873-895`）第一行就是 `stopLocationUpdates()`，重复调用安全；
- 恢复后第一个点被 `skipNextAcceptedPoint` 丢弃，不会产生"暂停点到恢复点"的假距离；
- `RunTrackingScreen` 里"继续"按钮在暂停时可点，无需改。

**风险与兜底**：client 重启失败（`startAmapLocationUpdates` 抛错）→ 保持暂停态并提示"定位恢复失败，请重试/结束本次跑步"，允许用户结束保存已跑部分。

**验证**：

1. 开始跑步 → 暂停 → 日志 5 分钟无 `raw location` 记录；
2. 电量页确认暂停期无 GPS 消耗；
3. 恢复后轨迹连续、没有跨越暂停位置的直线段；
4. 暂停 30 分钟后结束保存，时长不含暂停段。

### 1.2 计时改用 `SystemClock.elapsedRealtime()`

**目标**：改系统时间 / NTP 校时 / 时区切换不再影响跑步时长；锁屏休眠仍正确计时；草稿恢复后时长连续。

**现状**：`activeDurationSeconds()`（`:829-832`）用 `System.currentTimeMillis()` 差值；`startTime`、`pausedAtMs` 都是墙上时钟。

**方案**：**双时钟分离**——墙上时钟只用于落库的"起点时刻"，计时全部走 elapsed。

新增/替换 Service 字段：

| 字段 | 含义 |
| --- | --- |
| `startWallClockMs` | 起点墙上时间，写 `exercise_records.startTime` |
| `startElapsedMs` | 本段计时基准（`SystemClock.elapsedRealtime()`） |
| `pausedAtElapsedMs` | 本次暂停开始的 elapsed 时刻（0 表示未暂停） |
| `totalPausedElapsedMs` | 本次累计暂停时长 |
| `baseDurationMs` | 草稿恢复时已经累计的时长 |

```kotlin
private fun activeDurationSeconds(): Long {
    val nowElapsed = if (pausedAtElapsedMs > 0L) {
        pausedAtElapsedMs
    } else {
        SystemClock.elapsedRealtime()
    }
    val activeMs = (nowElapsed - startElapsedMs - totalPausedElapsedMs).coerceAtLeast(0L)
    return (baseDurationMs + activeMs) / 1000L
}

// startTracking()
startWallClockMs = System.currentTimeMillis()
startElapsedMs = SystemClock.elapsedRealtime()
pausedAtElapsedMs = 0L
totalPausedElapsedMs = 0L
baseDurationMs = 0L

// pauseTracking()
pausedAtElapsedMs = SystemClock.elapsedRealtime()

// resumeTracking()
totalPausedElapsedMs += SystemClock.elapsedRealtime() - pausedAtElapsedMs
pausedAtElapsedMs = 0L

// continueDraftTracking()
startWallClockMs = draft.startTime
baseDurationMs = draft.durationSeconds * 1000L
startElapsedMs = SystemClock.elapsedRealtime()   // 从恢复瞬间重新计时
pausedAtElapsedMs = 0L
totalPausedElapsedMs = 0L
```

**草稿兼容**：`run_draft` 表已有 `durationSeconds`、`startTime`，恢复时把 `durationSeconds` 作为 `baseDurationMs` 即可，**不需要改表结构**；`draft.pausedAtMs`/`totalPausedMs` 变成"仅记录用"，恢复逻辑不再依赖它们（保存到恢复之间的空档天然不计时）。

**同步改调用点**：`activeDurationSeconds(now)` 目前有两处带参调用——`continueDraftTracking()`（`:411`）和 `startTimer()`（`:733`），改成无参版本后一并更新；`saveDraftTracking` / `persistDraftSnapshot` 继续读 `current.durationSeconds`，无需改。

**落库的起止时间**：`startTime = startWallClockMs`，`endTime = startTime + durationSeconds * 1000`（与现在 `saveRun` 的算法一致，避免与时长口径打架）。

**风险**：`elapsedRealtime` 包含深睡时间（默认 `includeDeepSleep = true`），与现有"睡多久算多久"的语义一致，不会改变用户预期；如需排除深睡可换 `elapsedRealtimeNanos` 的 `deepSleep` 版本，但一般不需要。

**验证**：

1. 跑步中把系统时间 +1 小时 → 时长不变；
2. 锁屏 10 分钟 → 时长正常增长；
3. 暂停 5 分钟 → 恢复后时长跳变 ≤1s；
4. 杀进程 → 草稿恢复 → 时长从草稿值继续累加；
5. 结束保存后 `exercise_records.durationSeconds` 与 HUD 一致。

### 1.3 通知权限降级为"警告"而非阻断

**目标**：没给通知权限也能跑步；页面给出明确提示，而不是把用户挡在门外。

**现状**：两处硬阻断——`RunTrackingViewModel.startTracking()`（`:92-97`）与 `RunTrackingScreen`（`:67`）。

**方案**：引入"非阻断提示"通道，与 `errorMessage` 区分开。

```kotlin
// RunModels.kt: RunTrackingUiState 新增
val warningMessage: String? = null
```

```kotlin
// RunTrackingViewModel.startTracking(): 删除 !hasNotificationPermission 分支
when {
    !permissions.hasLocationPermission -> { /* 保留阻断 */ }
    !locationEnabled -> { /* 保留阻断 */ }
    else -> {
        if (!permissions.hasNotificationPermission) {
            RunTrackingStateStore.update {
                it.copy(warningMessage = "通知权限未开启，息屏时可能看不到跑步进度")
            }
        }
        ContextCompat.startForegroundService(appContext, RunTrackingService.startIntent(appContext))
    }
}
```

- `RunTrackingScreen.kt:65-70`：首屏只请求**定位**权限；通知权限改为点"开始"时静默请求一次，被拒就设置 `warningMessage`，不再中断。
- HUD：在 GPS 状态行下方加一行 12sp 的提示（`warningMessage`），开始后 5 秒自动消失或点击关闭。
- 权限说明仍保留在设置入口（可选）。

**风险**：Android 13+ 前台服务无通知时会在通知栏隐藏入口——这是系统行为，用户从最近任务仍能看到；提示文案要写清"息屏可能被系统回收"，并保留"去开启"按钮。

**验证**：拒绝通知权限 → 仍能开始 → 通知栏无通知但 HUD 有提示 → 跑步/保存正常。

## 2. P1 一致性与健壮性

### 2.1 字距 / 溢出 / ripple「三件套」

这三件事同源：**文本与点击反馈都依赖主题默认值，没有项目自己的约定**，所以每加一行文案、每加一个卡片都会重新踩坑（本轮已踩两次）。

#### 2.1.1 字距：数值文本统一 style

```kotlin
// ui/theme/Type.kt
/** 数值型文本：等宽数字 + 零字距 + 固定行高，避免继承 bodyLarge 的 0.5sp。 */
val NumericText = TextStyle(
    fontFeatureSettings = "tnum",
    letterSpacing = 0.sp,
    lineHeight = 16.sp
)
```

推进顺序：

1. 先把 `ExerciseTabularNumbers`（`ExerciseScreen.kt:56`）替换为 `NumericText`，应用到记录行、统计卡、HUD 数值；
2. 观察一轮截图后，把 `Typography.bodyLarge.letterSpacing` 从 `0.5.sp` 改为 `0.sp`（`Type.kt:16`），全局收紧；
3. 若担心视觉变化，可先只做第 1 步——它已经能消除"数值行多一位就溢出"的问题。

#### 2.1.2 溢出：两段式行 + 显式省略号

建立两个约定，替代"一行塞三段信息"：

```kotlin
// 关键信息不允许被压缩时：拆成两个 Text
Row(verticalAlignment = Alignment.CenterVertically) {
    Text(
        text = "00:57:00 · 12'44\"",
        maxLines = 1, softWrap = false, overflow = TextOverflow.Ellipsis,
        modifier = Modifier.weight(1f, fill = false)
    )
    Spacer(Modifier.width(4.dp))
    Text("449 kcal", maxLines = 1, softWrap = false)   // 不参与压缩
}

// 说明型单行：显式 ellipsis，让用户看到"还有内容"
Text(text = ..., maxLines = 1, overflow = TextOverflow.Ellipsis)
```

适用位置：记录行元信息（`ExerciseRecordItems.kt:235`）、月卡头部「累计 N 次 · X 小时」、统计详情卡 subline、首页卡片副标题。

#### 2.1.3 ripple：统一 `appClickable`

现状：裸 `Box + clickable` 的 ripple 取 `LocalContentColor`（默认黑），深色背景上不可见；分段按钮已用"按下态背景"绕过。

```kotlin
// ui/components/AppClickable.kt
private val AppRippleColor = Color.White.copy(alpha = 0.16f)

fun Modifier.appClickable(
    enabled: Boolean = true,
    onClickLabel: String? = null,
    onClick: () -> Unit
): Modifier = composed {
    val interaction = remember { MutableInteractionSource() }
    clickable(
        interactionSource = interaction,
        indication = ripple(color = AppRippleColor),   // material3 1.3.0 可用
        enabled = enabled,
        onClickLabel = onClickLabel,
        onClick = onClick
    )
}
```

- 依赖版本确认：`composeBom = 2024.09.00` → material3 1.3.0，`ripple(color = ...)` 可用；
- 替换范围（按文件分批）：`HomeScreen` 各卡片、`ExerciseRecordItems` 行、`ExerciseScreen` 统计卡与分段按钮、`WeightCards`、`WeightRecordComponents`；
- 分段按钮的"按下态背景"可以保留，或统一改为 ripple（二选一，别叠加两种反馈）；
- 顺带：给按钮类加 `Modifier.minimumInteractiveComponentSize()`，保证 48dp 触控。

**风险**：替换面广、涉及视觉回归。建议按页面分批，每批跑一次真机截图对比；`ripple` 颜色统一后要确认在绿色卡 / 深色卡上都可见。

**验证**：逐页点一遍，确认按下有可见反馈；对比替换前后截图；无障碍测试（TalkBack 朗读"按钮"）。

### 2.3 体重目标方向 + 同日覆盖提示

#### 2.3.1 双向目标

```kotlin
fun calculateTargetProgress(first: Double?, current: Double?, target: Double?): Float? {
    if (first == null || current == null || target == null) return null
    val total = abs(target - first)
    if (total <= 0.0001) return null
    val moved = if (target >= first) current - first else first - current
    return (moved / total).toFloat().coerceIn(0f, 1f)
}

fun remainingWeight(current: Double?, target: Double?): Double? =
    if (current == null || target == null) null else abs(current - target)

/** 文案：v1 需要"还需减 / 还需增 / 已达成"三种状态。 */
fun targetProgressText(current: Double?, target: Double?): String {
    if (current == null || target == null) return "未设置"
    val remaining = current - target
    return when {
        abs(remaining) < 0.05 -> "已达成"
        remaining > 0 -> "还需减 ${formatWeight(remaining)} kg"
        else -> "还需增 ${formatWeight(abs(remaining))} kg"
    }
}
```

## 3. P2 性能与工程化

### 3.1 轨迹点 O(N²) 追加 + 分批入库

**问题**：`handleLocation()` 里 `current.trackPoints + result.point`（`RunTrackingService.kt:669`）每点复制整表；2 小时约 7200 点 → 约 2600 万次元素拷贝，且每秒一次全量 StateFlow 通知。

**方案 A（推荐）：换持久化列表**

```kotlin
// gradle/libs.versions.toml
kotlinx-collections-immutable = "0.3.8"
// build.gradle.kts
implementation("org.jetbrains.kotlinx:kotlinx-collections-immutable:0.3.8")

// RunModels.kt
val trackPoints: PersistentList<RunTrackPointUiModel> = persistentListOf()

// RunTrackingService.handleLocation
val points = current.trackPoints.add(result.point)   // 结构共享，O(log32 n)
```

优点：`PersistentList` 实现了 `List`，HUD/渲染器/保存逻辑的调用点基本不用改（`.size`、遍历、`last()` 都可用）；缺点是新增一个小依赖（约 100KB）。

**方案 B（不想加依赖）：分块列表**

```kotlin
// 每 128 点一块，只有最后一块被复制
val chunks: List<List<RunTrackPointUiModel>>
```
代价是渲染器/保存/HUD 都要改成"摊平后使用"，改动面比 A 大。

**分批入库**：`saveRun()`（`:628`）把 `insertTrackPoints(points)` 拆成 500 条/批循环（SQLite 单语句变量上限 999）：

```kotlin
points.chunked(500).forEach { chunk -> database.runDao().insertTrackPoints(chunk.map { it.copy(sessionId = id) }) }
```

**验证**：

1. 用 1 万点伪造数据跑 `handleLocation` 基准（或真机长跑抓 profile），对比改动前后 GC/CPU；
2. 结束保存耗时（目标 <300ms）；
3. 内存峰值不随点数线性增长（持久化列表仍会占内存，但不再有 N 份拷贝）。

### 3.2 统计查询下推与缓存

**问题**：`ExerciseViewModel.observeStatsDetail()` 每次翻页都 `observeAllExercises().map { buildExerciseStatsDetail(...) }`，重复聚合全表。

**方案**：

1. Room 查询下推——`ExerciseDao` 增加按时间区间查询：
```kotlin
@Query("SELECT * FROM exercise_records WHERE startTime BETWEEN :start AND :end ORDER BY startTime")
fun observeExercisesBetween(start: Long, end: Long): Flow<List<ExerciseRecordEntity>>
```
2. 在 ViewModel 里缓存最近 3 期的 `ExerciseStatsDetailUiState`（`LinkedHashMap` + 记录集变化时清空），翻页时命中缓存直接返回；
3. `periodOffset` 变化只触发一次查询（`flatMapLatest` + `distinctUntilChanged`）。

**两个配套改动**（否则下推会缺数据）：

- `canGoPrevious` 需要"最早一条记录"，单独加一个轻量查询：
```kotlin
@Query("SELECT MIN(startTime) FROM exercise_records")
fun observeEarliestStartTime(): Flow<Long?>
```
- 区间边界依赖"offset → 起止时间"的换算，目前这段逻辑是 `ExerciseStats.kt` 里的私有函数（`buildStatsPeriodRange`）；需要提升为 `internal` 供 ViewModel 复用，避免两处各写一套周/月/年边界。

**验证**：翻 10 页的数据库查询次数从 10 次全表降到 10 次区间；页面切换无可感知延迟。
