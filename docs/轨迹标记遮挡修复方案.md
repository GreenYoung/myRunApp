# 轨迹标记遮挡（GO/END、里程点）修复方案

> 整理日期：2026-11-17
> 范围：`feature/run` 的地图标记渲染（实时跑步页 + 历史轨迹预览/详情页）
> 状态：**仅方案，未改代码**。行号基于当前工作区。
> 一句话结论：这不是"偶发 z 序问题"，而是**标记直接钉在经纬度上、完全没有屏幕空间避让**导致的必然遮挡；GO/END 可以用「旗标 + 上下锚点错位」一次性根治，里程点需要「优先级 + 同簇聚合」。

---

## 0. 结论摘要

| 现象 | 根因 | 推荐做法 | 是否要碰撞检测 |
| --- | --- | --- | --- |
| 「GO」有时被盖住 | GO 的 zIndex 最低（20），END（21）、里程点（22）、当前位置（30）任意一个落在同一位置就会盖住它；环线/折返跑时终点必然≈起点 | 把 GO/END 从"中心锚定的圆形文字"改成**旗标贴图**，GO 用 `anchor(0.5, 1.0)` 向上展开、END 用 `anchor(0.5, 0.0)` 向下展开，两点重合也互不遮挡 | 只解决 90%：极近但不重合时再加一个合并兜底 |
| 里程点 1、2、3… 被盖住 | 所有公里标记 `zIndex = 22f` 且按编号顺序添加，位置重合时**后加的（编号大的）永远盖住先加的**；操场多圈、折返路线会让不同公里落在同一坐标 | 引入**标记布局层**：按优先级在屏幕空间逐点判定，同簇只保留一个标签（取最大编号）+ 其余降级为小圆点；缩放变化后重排 | 需要 |

两条关键判断：

1. **zIndex 调顺序解决不了问题**。用户要的是"两个都看得见"，而 zIndex 只能决定谁在上——同一点上的两个 28dp 圆，无论怎么调，总有一个被完全盖住。
2. **遮挡只在屏幕空间有意义**。同一对坐标在 zoom 18 相距 40px、在 zoom 14 只相距 2px，所以判定必须用 `projection.toScreenLocation()` 的像素距离，并且**只在缩放变化时重排**（纯平移不改变相对距离，见 4.3）。

## 1. 现象与复现场景

「有时候」并不是随机，而是**轨迹形状 + 当前缩放**共同决定：

| 场景 | GO/END | 里程点 |
| --- | --- | --- |
| 操场绕圈（400m × 12 圈） | 终点回到起点，END 压住 GO | 每 2.5 圈一个公里的位置循环：km1/km3/km5… 落在同一处，km2/km4/km6… 与起点同处 |
| 折返跑（2km 折返 × 2） | 终点回到起点 | km1/km3 在同一处，km2 在折返点、km4 在起点 |
| 环线（起点即终点） | 完全同点 | 视环长而定，长环可能不重叠 |
| 直线单程 | 不重叠 | 1km 间隔，几乎不重叠 |

对应到代码：`AMapTrackPreview`（历史页）走 `drawSportTrack()`，每次 `clear()` 全量重建；`AMapRunTrackingMap`（实时页）走 `AMapLiveTrackRenderer` 增量添加。两套都没有"布局/避让"这一步。

## 2. 根因定位

### 2.1 标记直接钉在经纬度上，没有屏幕空间布局

| 位置 | 代码 | 说明 |
| --- | --- | --- |
| `AMapRunTrackRenderer.kt:99-106` | GO | `.position(...).anchor(0.5f, 0.5f)`，28dp 圆以点为中心 |
| `:114-123` | END | 同上，`zIndex(21f)` |
| `:361-386` | 公里点 | 同上，18dp 圆，`zIndex(22f)` |
| `:210-217` | 当前位置 | 30dp 圆，`zIndex(30f)` |

`anchor(0.5f, 0.5f)` 意味着圆心就在坐标点上，两个距离小于 28dp 的点（GO/END）或 18dp 的点（公里点）必然叠在一起，**没有任何代码检测这种重叠**。全工程也搜不到 `projection` / `toScreenLocation` / `OnCameraChange`，说明目前完全没有屏幕空间的概念。

### 2.2 zIndex 把优先级写反了

当前固定值：`GO = 20 < END = 21 < 公里点 = 22 < 当前位置 = 30`。

结果是**越不重要的越在上面**：环线时 END 压 GO；折返时 km4 压 GO；刚起跑时当前位置点压 GO。用户看到的"GO 被覆盖"其实是 z 序的固定结果，不是偶发。

### 2.3 公里点之间 zIndex 完全相同

`zIndex` 都是 `22f`，同值时由添加顺序决定层级：`points.zipWithNext()` 顺序 → **编号大的后添加 → 编号大的盖住小的**。操场第 5 圈时，同一位置的 km3 会盖掉 km1。

### 2.4 两套渲染器都不具备"布局"步骤

- `drawSportTrack()`（`:81-126`）：`clear()` 后按 固定顺序 / points 顺序 直接 `addMarker`，没有候选集合、没有冲突判定。
- `AMapLiveTrackRenderer`（`:529-750`）：跑到里程点时逐个 `addMarker` 并立即生效，**已添加的标记无法回头调整**，因为既没有保存句柄语义上的"标签列表"，也没有重排入口。

### 2.5 顺带发现：实时页的 LIVE 标签也被压住

追踪中终点标签文案是 `LIVE`（`:674`），位置就是最后一个点；而当前位置 marker（`:719-726`）`zIndex = 30` 在同一位置，LIVE 的红色圆圈和文字基本被当前位置的绿色圆点+光晕盖住。属于同一类问题，建议一起处理。

## 3. 方案对比

| 方案 | 做法 | 解决 GO/END | 解决里程点 | 工作量 | 风险 |
| --- | --- | --- | --- | --- | --- |
| 0. 只调 zIndex | GO 提到最高 | 只把"GO 被盖"换成"END 被盖" | 无改善 | 5 分钟 | 看似修好、实际更糟 |
| **A（推荐）** | GO/END 改旗标 + 上下锚点错位；公里点加优先级避让与同簇聚合 | ✅ 根治 | ✅ 解决 | 中（~1 天） | 低，可开关回退 |
| B（进阶） | 在 A 基础上，冲突标签用引线扇形外扩，全部数字可见 | ✅ | ✅ 全部保留 | 中大（+1~2 天） | 标签漂移、需更频繁重排 |

**推荐 A**：问题 1 用锚点错位，几乎零风险且完全不依赖地图投影；问题 2 只在缩放变化时做一次 O(n²) 的吸附（n 最多几十个，耗时 <1ms）。

## 4. 方案 A 细则

### 4.1 起终点（问题 1）：旗标 + 上下锚点错位

把 GO/END 从「以点为中心的圆形文字」改成「带指针的旗标贴图」，用原点位置锚定指针尖：

| 标记 | 贴图 | anchor | 视觉效果 |
| --- | --- | --- | --- |
| GO | 圆角胶囊 + 下方小三角，绿色 | `(0.5f, 1.0f)` | 标签整体浮在坐标点**上方**，指针尖指向起点 |
| END | 同上，红色 | `(0.5f, 0.0f)` | 标签整体挂在坐标点**下方** |

这样即使起点与终点完全重合（环线/操场），两个标签一个向上、一个向下，**不可能互相遮挡**，也不需要任何碰撞检测。同时在追踪刚起步时，当前位置的绿点压在点上、GO 旗标浮在上方，也不再互相挡。

细节：

- 贴图尺寸从 28dp 正方改为约 34dp × 40dp（含指针），文字 8.5sp 不变；`MarkerOptions.anchor` 必须同步改成上面两个值，否则位置会整体偏移。
- `TrackBoundsPadding`（`AMapRunTrackRenderer.kt:36`，当前 `58` 是**像素**，3x 屏约 19dp）需要相应加大：旗标高约 40dp ≈ 120px，会超出当前留白导致贴边的起终点被裁；建议改为按密度计算（如 `(36 * density).roundToInt()`），并在真机上看边界效果。
- zIndex 调整：`GO = 41`、`END = 40`、公里点 = 30、当前位置 = 45（当前位置保持最顶，因为它是实时信息且不是文字标签）。
- 兜底：若起点与终点屏幕距离 < 10dp 且都是旗标，可改为单个 `GO·END` 合并胶囊（`createRouteLabelMarkerBitmap` 需要支持"圆角矩形 + 按文本测量宽度"的绘制模式）。这一步可选，先上线旗标方案观察真机效果再决定要不要加。

### 4.2 里程点（问题 2）：优先级 + 同簇聚合

引入一个"标记布局"步骤，输入是候选标签，输出是"实际要画的标签"：

```kotlin
internal enum class TrackLabelKind { START, END, START_END, KILOMETER, CURRENT }

internal data class TrackLabelSpec(
    val kind: TrackLabelKind,
    val latLng: LatLng,
    val text: String,
    val kilometer: Int? = null
)

internal data class PlacedTrackLabel(
    val kind: TrackLabelKind,
    val latLng: LatLng,
    val text: String,
    val zIndex: Float,
    val isDot: Boolean = false        // true = 降级为 4dp 小圆点，不显示文字
)
```

判定规则（`resolve(specs, project, density)`）：

1. **优先级**：起终点（START_END/START/END）> 当前位置 > 公里点（编号小的优先）。
2. **依次接受**：从高优先级开始遍历，计算候选点与"已接受标签"中心的像素距离；全部 ≥ 阈值则接受，否则进入冲突处理。
3. **阈值**：起终点 30dp、当前位置 24dp、公里点 22dp（按 `density` 换算成 px；公里点圆 18dp，留 4dp 间距）。
4. **公里点冲突 → 同簇聚合**：
   - 与已接受的公里标签距离 < 阈值时，归入该"位置簇"；
   - 簇最终只保留**一个**标签，文案取簇内**最大编号**（例：操场同一位置有 1/3/5… 时显示最新的「11」）；
   - 簇内其余点降级为 4dp 小圆点（`isDot = true`），保留"这里有公里刻点"的信息，不显示数字。
   - 不推荐显示 `1-11` 这种范围：这些编号不是连续区间（实际是 1、3、5、7…），会被误读成"1 到 11 公里"。
5. **公里点撞上起终点或当前位置** → 直接降级为小圆点，不参与聚合。
6. **`projection` 不可用**（地图未布局/首帧）→ 退化为"全部显示"，保持现有行为，不阻塞渲染。

实时页的额外约束：标记是跑动中逐个追加的，所以布局层必须**保存 placeholder → Marker 句柄**，冲突解除（例如用户放大）时能把小点重新变回文字标签；不能只做"添加时判断一次"。

### 4.3 什么时候重算（避免重排风暴）

关键结论：**纯平移不会改变两个标记之间的屏幕距离**。地图 SDK 的 `moveToRoadLevel` 每秒都会把相机移到最新点（`AMapRunTrackingMap.kt:240-283`），如果每次相机变化都重排，实时页会持续抖动。

所以只在以下三种情况重排：

1. 点集变化（新点、清空、重画）；
2. **zoom 变化超过阈值**（如 `abs(newZoom - lastZoom) > 0.05f`）；
3. 视图尺寸变化（旋转、分屏）。

实现上用 `map.setOnCameraChangeListener { onCameraChangeFinish }` 比较 zoom 即可，不需要 debounce（`onCameraChangeFinish` 本身在惯性结束后触发一次）。

### 4.5 实时页 LIVE 标签（顺带）

三种可选，推荐第 2 种：

1. 保持现状（被当前位置点盖住，等于没有）；
2. **追踪中不画 LIVE 标签**——当前位置的绿点本身就是"我在这"，红色 LIVE 反而和终点语义混淆；结束时（`isTracking = false`）再画红色 END 旗标；
3. 保留 LIVE，但把贴图改成挂在点右侧的小胶囊（`anchor(0f, 0.5f)`），避开绿点。

## 5. 方案 B（后续可选，先不做）

在 A 之上把"隐藏/聚合"改成"外扩 + 引线"：

- 每个冲突标签沿以冲突点为圆心的固定角度（`index * 60°`）偏移 22dp，并用 1dp 细线连回真实点；
- 优点：km1/km3 这类都能看到；
- 代价：放大回到低冲突状态时标签要缩回（重排更频繁）、屏幕上出现放射线可能与轨迹视觉冲突、zoom 变化时标签位置漂移。
- 建议：先用 A 上线，观察是否真的有必要保留每个编号；多数用户只看"总里程"和"最近公里"，聚合后取最大编号已够用。

## 7. 验证方案

### 7.1 构造四类轨迹（可用伪造 `RunTrackPointUiModel` 列表，或真机跑）

1. 400m 操场 12 圈（5km）—— 里程点 3 处循环、终点回起点；
2. 2km 折返跑（4km）—— km1/km3 同点、km2/km4 与起点同点；
3. 环线（起点即终点，且不是整数公里）；
4. 直线单程 3km —— 基线，不应出现任何降级。

### 7.2 检查点

- [ ] 场景 1/2/3：GO 与 END 同时可见，无互相遮挡（旗标上下分离）。
- [ ] 场景 1/2：同一位置的公里标记只显示一个数字（取最大编号），其余为小圆点。
- [ ] 缩放到 13 / 15 / 17 / 18.8 各档：放大后原本被聚合的公里点应逐步恢复成数字；缩小后应重新聚合，且不出现"两个数字叠在一起"。
- [ ] 实时页跑动中：经过 1km、2km 时新公里点出现位置正确；相机跟随平移时标签不闪烁；刚起跑时 GO 旗标与当前位置绿点都不被挡。
- [ ] 结束跑步进入详情页（`drawSportTrack` 全量渲染）：与实时页表现一致。
- [ ] 旋转屏幕 / 切后台再回：旗标不偏移、不重复添加。
- [ ] 弱网/无定位时 `projection` 不可用的首帧：退化为"全部显示"，不崩溃。

### 7.3 可自动化的部分

`resolveTrackLabels()` 是纯函数，单测覆盖：

- 同点 GO/END（屏幕距离 0）→ 仍输出两个标签（靠 anchor 分离，不在布局层合并）；
- 公里点三点同簇 → 输出 1 个数字 + 2 个小点，且数字为最大编号；
- 公里点撞起终点 → 降级为小点；
- 阈值边界（21.9dp / 22.1dp）；
- `projection` 为 null → 原样输出。

## 8. 风险与回退

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 旗标贴图导致位置偏移 | `anchor` 忘了同步改，标记会整体偏 20dp | 贴图与 anchor 一起进 `MarkerOptions` 构造，抽成一个函数，禁止散落调用 |
| 相机回调与重画互相触发 | `AMapTrackPreview.update` 目前每次重组都重画 | 先做 4.4 里的重画去重，再加相机监听 |
| 重排导致实时页闪烁 | 相机每秒移动 | 只在 zoom 变化 > 0.05 时重排（4.3） |
| `map.clear()` 后旧句柄失效 | 全量渲染会清掉所有 marker | 句柄列表在每次 `clear()` 后置空，`relayout()` 前判空 |
| `projection` 首帧无效 | 地图未布局时可能返回 (0,0) | 用 `visibleRegion` 有效性判断，无效则跳过避让 |
| 视觉回归 | 旗标比圆点更占空间，密集轨迹更"花" | 保留 `TrackMarkerStyle` 常量开关，可一键回到圆形标签 |

---

## 9. 建议实施顺序

1. 旗标贴图 + anchor 错位 + zIndex 重排（解决问题 1，可独立上线验证）；
2. `TrackLabelLayout` + 公里点聚合（解决问题 2 的核心）+ 单测；
3. 相机 zoom 变化重排 + `AMapTrackPreview` 重画去重（解决"放大后不恢复"的体验问题）；
4. 实时页 LIVE 标签处理（4.5）+ 真机联调。

前两步就能覆盖用户反馈的两个问题；第 3 步决定"放大/缩小后是否智能"，第 4 步是顺手收拾同类问题。

### 10.2 与方案的两处偏差（均为主动收窄）

| 方案原文 | 实际实现 | 原因 |
| --- | --- | --- |
| 优先级里包含「当前位置」，里程点撞当前位置也降级 | **当前位置不参与布局**，只靠 zIndex 压在最上层 | 当前位置每秒移动，纳入布局会导致每秒重排；它本身只是"我在这"的指示点，临时盖住某公里标签属于合理表现 |
| 兜底"GO·END 合并胶囊" | **未实现** | 旗标上下分离后，同点也不重叠；合并会额外增加贴图与判定分支，等真机确认确有需要再加 |
| 追踪中处理 LIVE 标签（给了 3 个选项） | 选择**选项 2：追踪中不画**，跑完才画 END | 旧的 LIVE 一直被 zIndex 更高的当前位置点压住，等于没有；当前位置的绿点已表达"我在这" |
