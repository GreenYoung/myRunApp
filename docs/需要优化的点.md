# MyRunApp 代码审查：BUG 与优化建议

> 审查日期：2026-10-23
> 审查范围：`app/src/main/java` 全部 Kotlin 代码、Room 迁移、AndroidManifest、Gradle 配置（约 1.2 万行）。
> 说明：本文只记录静态审查发现的问题，未包含真机回归结果；行号基于当前工作区代码（含未提交改动）。

## 结论摘要

| 级别 | 数量 | 说明 |
| --- | --- | --- |
| P0 高 | 9 | 会导致数据丢失、卡死、功能不可用或明显的错误结果，建议优先修复 |
| P1 中 | 8 | 数据一致性、边界条件和体验问题 |
| P2 性能 | 7 | 长历史数据 / 长跑场景下的卡顿、耗电和内存问题 |
| P3 工程化 / 安全 | 8 | 稳定性收尾、测试、日志与隐私合规 |

---

## 一、高优先级（P0）

### 1. 子页面没有处理系统返回键，按返回会直接退出 App

**位置**：`MainActivity.kt:80-107`、`ui/components/SwipeBackContainer.kt:16-74`

**现象**：
- 页面切换是手写的 `AppDestination` 枚举 + `when`，没有使用 Navigation，也没有 `BackHandler` / `OnBackPressedDispatcher`。
- `SwipeBackContainer` 只实现了"从右边缘左滑"手势，没有接管物理返回键 / 手势返回。
- 因此：在运动详情、体重详情、体重趋势、记录详情、统计详情页按系统返回键，会直接退出 Activity 回到桌面，而不是返回上一级。
- 跑步页按返回同样会退出 Activity（跑步服务继续后台记录，但用户会以为已退出）。

**建议**：在 `MainActivity` 中根据 `destination` 注册 `BackHandler(enabled = destination != Home) { navigateBack() }`；跑步页单独处理（返回时留在后台继续跑，或弹窗确认"继续/结束/放弃"）。

---

### 2. 保存跑步结果存在竞态，UI 可能永远停在"保存中"

**位置**：`feature/run/RunTrackingViewModel.kt:115-134`、`feature/run/RunTrackingStateStore.kt:14-15,25-27`

**原因**：
- `RunTrackingStateStore.savedSessionIds` 是 `MutableSharedFlow(extraBufferCapacity = 1)`，**`replay = 0`**。
- `finishTracking()` 先调用 `startService(finishIntent)`，再在协程里 `savedSessionIds.first()` 等待结果。
- SharedFlow 在**没有任何订阅者**时，`tryEmit` 的返回值是 `true` 但事件会被直接丢弃（buffer 只对慢速订阅者生效）。
- 如果 Service 保存得很快，在 `first()` 订阅前就 `emitSavedSessionId`，这一次事件会丢失，`first()` 将永久挂起；之后用户再保存一次时，这个"遗留协程"会收到下一次的 sessionId 并触发意外跳转。
- 如果 Service 保存失败（未 emit），同样永久挂起。

**建议**：不要用"事件流"传结果。改为：
- `MutableSharedFlow(replay = 1)`（仍要注意重复消费问题）；或
- 用 `CompletableDeferred<Long>` / 回调 / `suspend fun finishAndWait(): Long`；或
- 由 Service 把结果写入 `RunTrackingStateStore`（含 `lastSavedSessionId` 与 `saveError`），ViewModel 直接用 `state` 等待状态变化。

---

### 3. 保存跑步失败时没有异常处理，`isSaving` 会永久为 true

**位置**：`RunTrackingService.kt:239-245,264-302`

**原因**：
```kotlin
serviceScope.launch {
    val sessionId = saveRun(current)
    isSaving = false
    RunTrackingStateStore.emitSavedSessionId(sessionId)
    RunTrackingStateStore.reset()
    stopForegroundAndSelf()
}
```
- `saveRun` 内部有 3 次数据库写入，任何一次抛异常都会让协程直接结束。
- 之后 `isSaving` 永远为 `true`，`stopForegroundAndSelf()` 不执行，**前台通知和跑步服务一直挂着**，按钮一直是"保存中..."，用户只能强杀 App。
- 而且 `exercise_records`、`run_sessions`、`run_track_points` 分 3 次独立写入，没有任何事务，失败会留下半条数据（孤儿运动记录 / 会话没有轨迹点）。

**建议**：
- `saveRun` 包 `try/catch`，失败时 `errorMessage = "保存失败，请重试"`、`isSaving = false`，并保留本次数据允许重试。
- 用 `database.withTransaction { ... }` 或 DAO 上的 `@Transaction` 方法，把三张表的写入合并成一个原子操作。

### 4. "放弃本次跑步"功能没有接线，跑错了无法取消

**位置**：`RunTrackingScreen.kt:100,114`、`RunTrackingViewModel.kt:101-103`

**现象**：
- `RunTrackingRoute` 把 `viewModel::stopWithoutSaving` 传给了 `RunTrackingScreen` 的 `onDiscard`，但 `RunTrackingScreen` 内部**从未使用 `onDiscard`**（只有 Preview 传了 `{}`）。
- 也就是说，用户开始跑步后只有"暂停/继续"和"长按结束保存"两个选择，没有"放弃"入口；一旦开始，只能保存或让后台一直跑。

**建议**：在跑步页增加"结束"或"放弃"入口（例如顶部菜单 / 二次确认弹窗），调用 `onDiscard`；或明确删除这个死参数，避免误导。

### 5. 进程被杀后跑步状态全部丢失，`START_STICKY` 重启的是"空服务"

**位置**：`RunTrackingService.kt:75-89,91-96`、`RunTrackingStateStore.kt:10-23`

**原因**：
- 实时轨迹、开始时间、累计距离都只存在内存单例 `RunTrackingStateStore` 中，进程被杀即全部丢失。
- 服务返回 `START_STICKY`，系统重启 Service 时 `intent == null`，`onStartCommand` 的 `when` 不匹配任何分支，服务什么都不做（也没有重新 `startForeground`），最终被系统回收。
- 如果只是 Service 被系统回收而进程还活着，`Store` 里仍是 `isTracking = true`、`isServiceRunning = true`，但计时器和定位都没了；此时点"开始跑步"会被 `if (RunTrackingStateStore.state.value.isTracking) return` 直接拦截，**用户无法重新开始**。

**建议**：
- 至少改为 `START_NOT_STICKY`；`onStartCommand(intent == null)` 时主动 `reset()` 并停止。
- 更完整的方案：每 N 秒 / 每 N 个点把进行中的跑步写入 Room（草稿表），进程恢复后可续跑或提示恢复；`onDestroy` 时也做一次落库。
- `startTracking()` 的提前返回要判断服务是否真的还在前台运行，而不是只信内存状态。

---

### 6. 编辑运动记录会篡改 / 丢失数据

**位置**：`ExerciseViewModel.kt:92-109,231-253`

四个相互独立的问题：

1. **时间被归零到 00:00**：新增跑步机记录时用"当前时刻"（`exerciseDateWithCurrentClockTime`），但编辑时走 `validation.startTime`，它是 `parseStartTime(date)` 的结果，即**当天 00:00:00**。编辑任何已有记录都会把开始时间改成0点（同一天内排序、展示时刻、后续统计都会受影响）。
2. **编辑户外跑步不会同步 `run_sessions`**：`saveExercise()` 只更新 `exercise_records`，`run_sessions` 里的 `distanceKm / durationSeconds / caloriesKcal / startTime` 完全不变。于是"运动列表 → 户外详情"用的是新值，"保存后 → 跑步轨迹详情"用的是旧值，**同一次跑步出现两份不同的成绩**。
3. **时长被按分钟截断**：`showEditDialog` 用 `(record.durationSeconds / 60L).coerceIn(1, 300)`，而编辑框只支持整分钟选择。一次 26 秒或 1 分 59 秒的跑步，打开编辑再保存就会变成 1 分钟/整分钟，累计里程时长统计被悄悄改写；超过 5 小时的记录会被截成 300 分钟。
4. **坡度丢失**：`showEditDialog` 把 `inputInclinePercent = ""`，而坡度没有入库。编辑一次跑步机记录后坡度按 0 计算，热量会被重算偏低。

**建议**：
- 编辑时保留原 `startTime`（只允许改日期时保留原"时分秒"）。
- 编辑带 `runSessionId` 的记录时同步更新 `run_sessions`；或禁止编辑有轨迹的记录（只允许改备注）。
- 时长编辑保留秒级精度，或明确"编辑后按分钟取整"并提示用户。
- 把坡度（以及跑带速度等）持久化到 `exercise_records`。

### 7. 体重目标只支持"减重"方向，增重目标显示为"未设置"

**位置**：`WeightLogic.kt:199-210`、`WeightScreen.kt:257-267`

**原因**：
```kotlin
fun calculateTargetProgress(firstWeight, currentWeight, targetWeight): Float? {
    val total = firstWeight - targetWeight
    if (total <= 0.0) return null      // 目标高于初始体重时为 null
    ...
}
fun calculateRemainingWeight(...) = (current - target).coerceAtLeast(0.0)
```
- 用户想从 60kg 增到 65kg 时，`targetProgress == null`，`TargetProgressBlock` 走"目标体重 / 未设置"分支，**明明设置了目标却显示未设置**。
- `remainingWeight` 在低于目标时被夹到 0，又显示"已达成"。

**建议**：进度按方向计算（`abs(target - first)` 作为总量，`abs(target - current)` 计算剩余），"剩余/超出"文案按 actual 与 target 的大小关系切换；或者产品上明确只支持减重并隐藏增重配置。

---

### 8. 允许录入未来日期，统计口径不一致

**位置**：`WeightLogic.kt:93-112`、`ExerciseLogic.kt:102`、`ui/components/ExerciseDatePicker.kt:141-177`、`ExerciseLogic.kt:184-190`

**现象**：
- 日期选择器没有最大日期限制，`validateWeightInput` / `validateExerciseInput` 也不校验 `date <= today`，用户可以录入明天、下个月的体重/运动。
- `buildExerciseSummary` 的今日有上界，但**本周/本月/总里程没有上界**：
  ```kotlin
  val weeklyRecords = records.filter { it.startTime >= weekStart }
  val monthlyRecords = records.filter { it.startTime >= monthStart }
  ```
  未来记录会被算进周/月目标和连胜/趋势，而 `buildExerciseRangeStats` 又用 `<= nowMillis` 过滤未来记录 → **同一页面两套口径**。
- 体重同理：`filterWeightPointsByRange` 只有下界，未来日期体重会进入"最新体重""本周变化"。

**建议**：日期选择器加 `maxDate = today` 并校验（若要支持补录，至少限制到"今天"）；统计统一加上上界 `<= now`。

---

### 9. 编辑体重记录更换日期可能覆盖另一条记录，且删除+写入不是事务

**位置**：`WeightViewModel.kt:256-271`

**原因**：
```kotlin
if (editingDate != null && editingDate != current.inputDate) {
    weightDao.deleteWeightByDate(editingDate)
}
val existing = weightDao.getWeightByDate(current.inputDate)
weightDao.upsertWeight(...)
```
- 把 A 日的记录改到 B 日时，如果 B 日**已有一条记录**，会直接 `Upsert` 覆盖 B 日记录，用户没有任何提示，原 B 日数据丢失。
- `deleteWeightByDate` 与 `upsertWeight` 是两次独立数据库操作，中途失败会丢记录。
- 体重记录的主键是 `date`，本质上是"每天一条"，编辑换日期更像是"合并"语义，需要明确产品规则。

**建议**：目标日期已存在记录时询问"合并/取消"；用 `@Transaction` 包裹删除+写入。

## 二、中优先级（P1）

### 10. 跑步时长依赖系统墙上时钟，改时间会跳变

**位置**：`RunTrackingService.kt:140,414-417`

`startTime` 取 `System.currentTimeMillis()`，计时用 `now - startTime - totalPausedMs`。用户中途修改系统时间、时区自动切换、NTP 校时，都会导致时长突跳（甚至变成 0）。建议改用 `SystemClock.elapsedRealtime()` 计时，展示时再与墙上时间分离。

---

### 11. 暂停时仍保持 GPS 定位，纯耗电

**位置**：`RunTrackingService.kt:306-309`

暂停后 `handleLocation` 只做丢弃，`AMapLocationClient` 仍以 1 秒间隔运行（还带文件日志）。建议暂停时 `stopLocation()`，恢复时重新启动并重新走起点校准（现有 `skipNextAcceptedPoint` + `reset()` 已支持）。

---

### 12. 地图页与地图组件未保存/恢复状态

**位置**：`AMapRunTrackingMap.kt:85-93`、`AMapTrackPreview.kt:37-47`

- `MapView` 用 `remember { MapView(context).apply { onCreate(Bundle()) } }` 创建，关闭 Activity/旋转时没有 `onSaveInstanceState` / `onCreate(savedState)`，旋转后地图视角丢失并重建。
- `RunTrackingScreen` 的 `mapDisplayType`、`autoFollow` 也是普通 `remember`，旋转后会重置。
- 建议使用 `rememberSaveable` 保存地图类型/跟随状态，并给 MapView 走标准 savedInstanceState 流程。

---

### 13. 体重"近 N 天"锚点不是今天，和运动关联范围不一致

**位置**：`WeightLogic.kt:170-188,257-288`

- `rangeStartDate` 以**最后一条体重记录的日期**往前推 N 天，而不是以今天为基准。如果用户一个月没称重，"近 7 天"展示的其实是一个月前的 7 天，但界面上写的是"近7天/本周"。
- `buildWeightExerciseCorrelation` 用同一个 `start7/start30` 过滤运动记录，但运动记录是"从该日期到**今天**"的全部数据，体重窗口与运动窗口长度不一致，结论（如"最近运动后体重下降"）可能失真。

**建议**：以今天为基准构造窗口，或至少给体重过滤也加上"结束日期 = 最新记录日期"，让两个维度使用同一区间；文案改为"最近一周数据"。

---

### 14. 统计详情可以无限向前翻空周期

**位置**：`ExerciseLogic.kt:423-429`

`canGoPrevious` 恒为 `true`，用户可以一直往前翻到没有任何记录的周期（比如 1970 年），没有边界。建议根据最早一条记录的日期计算最小 offset。

---

### 15. 前台通知的小图标使用自适应启动图标

**位置**：`RunTrackingService.kt:531-539`

`setSmallIcon(R.mipmap.ic_launcher)` 引用的是自适应图标（mipmap-anydpi-v26），在通知栏/状态栏可能显示为空白或方框（小图标要求单色 drawable）。建议增加一个专用的 `ic_stat_run.xml`/`ic_notification` 资源。

---

### 16. 通知权限被拒时直接禁止开始跑步，过于严格

**位置**：`RunTrackingViewModel.kt:64-99`、`RunTrackingScreen.kt:545-547`

Android 13+ 前台服务通知本身不受 `POST_NOTIFICATIONS` 阻断（服务仍可运行，只是通知不展示）。当前实现里通知权限被拒就完全不能跑步，对有"不想收通知"习惯的用户不友好。建议改为警告提示 + 仍允许开始。

---

### 17. 跑步页进入时的权限检查读到的是旧快照

**位置**：`RunTrackingScreen.kt:83-88`

```kotlin
LaunchedEffect(Unit) {
    viewModel.refreshPermission()
    if (!uiState.hasLocationPermission || !uiState.hasNotificationPermission) { ... }
}
```
`refreshPermission()` 更新的是 StateFlow，但本协程后续读取的 `uiState` 是**进入组合时的旧快照**，因此即使权限已授予，也可能再次弹出权限请求（或显示错误按钮状态）。建议把权限检查放进 ViewModel 或在 `rememberUpdatedState`/`snapshotFlow` 中读取最新值。

---

### 18. 地图销毁后仍可能执行延迟任务

**位置**：`AMapRunTrackingMap.kt:233-272`

`mapView.postDelayed({ moveToCurrentLocation(...) }, 350L)` 在页面退出（`onDestroy`）后仍可能执行，属于对已销毁 MapView 的操作，存在偶发崩溃/空指针风险。建议在 `DisposableEffect` 里维护 `destroyed` 标志，post 前判断。

---

## 三、性能优化（P2）

### 19. 运动页一次性加载全部轨迹点，并每次重算全部记录

**位置**：`ExerciseViewModel.kt:37-60`、`RunDao.kt:28-29`、`ExerciseLogic.kt:216-262`

- `ExerciseViewModel.uiState` 把 `runDao.observeAllTrackPoints()`（**所有会话的全部 GPS 点**）放进组合流，再在 `buildExerciseDetail` 中为每条记录映射轨迹点。
- 这个计算在 **每次输入框输入一个字符**（`inputState` 变化）时都会全量重跑一次。跑量数据积累后（几万点）会出现明显卡顿和内存压力。
- 列表页其实并不需要轨迹点；`observeRecordDetail` 已经按记录单独加载。

**建议**：
- 从首页/列表的 `uiState` 中移除 `observeAllTrackPoints()`，只在 `ExerciseRecordDetailRoute` 中按需查询。
- 把表单输入状态与统计状态分离，避免每次击键触发统计重算（或使用 `debounce` / `distinctUntilChanged`）。
- 删除 `buildExerciseDetail` 内部重复调用的 `buildExerciseSummary`（`ExerciseLogic.kt:222`）。

### 20. 体重历史计算为 O(n²)，也在每次击键时全量重算

**位置**：`WeightViewModel.kt:57-82`（`recentRecords` / `trendRecords`）

每条记录都执行一次 `records.filter { it.date < record.date }.maxByOrNull { it.date }`。记录数上千后会变成百万级比较，并且同样受 `inputState` 击键触发。建议一次遍历维护"上一条"（排序后 `zipWithNext`），并分离表单状态。

### 21. 文件日志在主线程同步写盘

**位置**：`core/log/FileLogWriter.kt:24-33`、`AppLogger.kt:38-41`

- `write()` 在调用线程 `synchronized` + `appendText`，而调用点大量位于 GPS 回调、Compose `LaunchedEffect`、ViewModel 主线程逻辑中。
- 跑步时每秒至少写入数条包含经纬度的日志，主线程 I/O 会造成掉帧、ANR 风险，也额外耗电。

**建议**：改为单线程 `Executor` + `BufferedWriter` 异步写入；或日志先用内存队列批量落盘。日志级别应可配置。

### 22. 实时轨迹每秒全量重绘 + 反复创建 Bitmap

**位置**：`AMapRunTrackingMap.kt:173-199`、`AMapRunTrackRenderer.kt:66-110,320-345,359-424`

- 每收到一个 GPS 点，`drawSportTrack()` 都会 `clear()` 并重建起点/终点/公里标记和整条 polyline；长跑时点复杂度持续上升。
- `createRouteLabelMarkerBitmap` / `createCircleMarkerBitmap` / `createCurrentLocationBitmap` **每次渲染都重新创建 Bitmap**，产生大量 GC 压力。
- 建议：实时页增量追加 polyline；Bitmap 按文字/颜色缓存（LruCache）；公里 marker 只在跨公里时追加；`MAX_RENDER_POINTS` 抽样仅用于历史轨迹。

### 23. 同时运行两个 AMapLocationClient

**位置**：`RunTrackingService.kt:458-480`、`AMapRunTrackingMap.kt:334-406`

记录服务和地图页各建了一个 1 秒间隔的定位客户端，跑步时同一时间有两套高精度定位在工作，耗电明显、日志翻倍，也可能出现地图位置与轨迹点短暂不一致。建议地图端直接从 `RunTrackingStateStore` 消费服务定位结果（或将定位封装为单一数据源）。

### 24. 数据库缺少索引

**位置**：`AppDatabase.kt:17-21`、`feature/run/data/RunDao.kt:22-32`

当前高频查询没有索引：
- `run_sessions.exerciseRecordId`（按运动记录反查会话）
- `run_track_points.sessionId`（按会话查轨迹、删除轨迹）
- `exercise_records.startTime`（列表排序、周期统计）
- `run_track_points.recordedAt`（`observeAllTrackPoints` 排序）

建议给实体加 `@Entity(indices = [...])` 并做一次数据库迁移（version 6）。

### 25. 频繁创建 `SimpleDateFormat`

`WeightLogic`、`ExerciseLogic` 等大量函数每次调用都 `SimpleDateFormat(...)`。单条记录格式化开销不大，但在 `buildExerciseDetail`/统计中按记录循环创建，属于可避免的分配。建议使用缓存的 `DateTimeFormatter`（`java.time`，minSdk 24 可用）或每次构建时复用一个 formatter。

## 四、稳定性与工程化（P3）

### 26. `RunTrackingService` 的 CoroutineScope 未取消

**位置**：`RunTrackingService.kt:50,91-96`

`onDestroy()` 只取消了 timer 和定位，`serviceScope` 没有 `cancel()`；`loadTrackingWeight`、`saveRun` 可能在服务销毁后继续访问数据库/更新全局状态。建议 `onDestroy` 中 `serviceScope.cancel()`。

### 27. 多表写入没有事务

- `RunTrackingService.saveRun`（运动记录 + 会话 + 轨迹点）
- `ExerciseViewModel.deleteExercise`（轨迹点 + 会话 + 运动记录）
- `WeightViewModel.saveWeight`（删除旧日期 + Upsert 新日期）

建议封装成 DAO 的 `@Transaction` 方法或 `db.withTransaction {}`，避免半成功状态。

### 28. `exportSchema = false`，迁移没有校验

**位置**：`AppDatabase.kt:20`

Room 的 schema 没有导出，升级时无法使用 `MigrationTestHelper` 验证；一旦手写迁移和实体不一致，只会在用户升级后崩溃。建议打开 `exportSchema = true` 并补充迁移测试（尤其 `MIGRATION_4_5` 增加 `note` 列）。

### 29. 测试覆盖过低

目前只有 `WeightLogicTest`（7 个用例）。建议为纯逻辑补充单测，成本低、收益高：
- `GpsTrackFilter`：静止漂移、跳点、暂停恢复、异常速度等（大量分支完全没有测试）。
- `ExerciseLogic`：周/月边界、未来日期、连胜计算、周期统计。
- `WeightLogic`：目标进度方向、范围过滤、BMI 边界。
- 数据库迁移测试。

### 30. 未使用的代码 / 参数

- `ExerciseViewModel.onTypeChange`（`ExerciseViewModel.kt:127`）—— 当前 UI 已移除类型选择器，方法未使用。
- `RunTrackingScreen.onDiscard`（见 P0-4）。
- `TargetWeightRepository.saveTargetWeight`（`TargetWeightRepository.kt:27`）未被调用。
- `WeightDao.observeLatestWeight`（`WeightDao.kt:13-14`）、`ExerciseDao.getAllExercises`（`ExerciseDao.kt:20-21`）未使用。

建议清理，避免后续误改。

### 31. 手势返回的 `pointerInput` key 不稳定

**位置**：`SwipeBackContainer.kt:35`

`pointerInput(onBack)` 中的 `onBack` 是 `MainActivity` 每次重组都会新建的 lambda，可能导致手势过程中输入检测被重启。建议 `val currentOnBack by rememberUpdatedState(onBack)`，以稳定 key 调用。

### 32. 日志调用不统一

## 五、安全与合规

### 34. Release 包仍开启文件日志，且日志包含精确 GPS 坐标

**位置**：`app/build.gradle.kts`（`buildTypes.release` 中 `ENABLE_FILE_LOG = true`）、`FileLogWriter.kt:24-33`

- 生产版本会持续把日志写到 `externalCacheDir/log/`，保留 7 天、最多 10 个 2MB 文件；日志中有 `lat/lon/accuracy`、数据库内容等。
- 建议：Release 关闭文件日志（或改为显式"导出诊断日志"开关），并对坐标做脱敏/截断。

### 35. 高德隐私合规接口硬编码为已同意

**位置**：`RunTrackingService.kt:66-67`、`AMapRunTrackingMap.kt:87-88`、`AMapRunTrackingMap.kt:355-356`、`AMapTrackPreview.kt:39-40`

```kotlin
AMapLocationClient.updatePrivacyShow(context, true, true)
AMapLocationClient.updatePrivacyAgree(context, true)
```
按高德 SDK 合规要求，这两个接口应在**用户明确同意隐私政策之后**再调用，并且需要提供隐私政策入口。当前直接传 `true` 等于替用户同意，存在合规风险。

### 36. `allowBackup = true` 且备份规则未排除健康数据
 
**位置**：`AndroidManifest.xml:15`、`res/xml/backup_rules.xml`、`res/xml/data_extraction_rules.xml`

体重、跑步轨迹属于个人健康数据，当前 Room DB 未加密且默认会被自动备份/设备迁移。若不希望数据离开设备，应在备份规则中排除数据库；若需要备份，应评估脱敏/加密策略。

### 37. 产物只包含 arm64-v8a

**位置**：`app/build.gradle.kts`（`ndk { abiFilters += "arm64-v8a" }`）

如果这不是刻意取舍，会导致 32 位老设备无法安装、**x86_64 模拟器也无法运行**（影响开发和自动化测试）。建议确认目标设备范围；如需模拟器调试可加 `x86_64`。

### 38. 数据库未加密

Room 数据库为明文，包含体重、身高、GPS 轨迹。若产品对隐私有要求，可考虑 SQLCipher；至少应在文档中明确数据仅本地存储的策略。

## 七、建议的回归验证点

- 各子页面（运动/体重/趋势/记录详情/统计详情/跑步页）按系统返回键的预期行为。
- 弱网/GPS 漂移场景下开始、暂停、恢复、结束；保存过程中杀进程 / 切后台。
- 保存失败（例如磁盘满）后按钮状态是否恢复、数据是否可重试。
